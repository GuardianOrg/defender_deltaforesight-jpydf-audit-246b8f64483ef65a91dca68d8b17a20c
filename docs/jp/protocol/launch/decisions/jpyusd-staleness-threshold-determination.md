# JPY/USD staleness threshold 設計


| 項目      | 値                                                                                                                 |
| ------- | ----------------------------------------------------------------------------------------------------------------- |
| 目的      | JPY/USD（全ブランチ共通レッグ）の `stalenessThreshold` を決定する                                                                   |
| スコープ    | 本書は **JPY/USD レッグの staleness threshold の値決定のみ**を扱う                                                                |
| 根拠      | Chainlink JPY/USD の mainnet 実更新履歴（2024-06-28〜2026-06-16・約 6,871 更新）の直接実測 ＋ 実装コード照合（Claude Opus 4.8・2026-06-17 実測） |
| 対象 feed | proxy `0xBcE206caE7f0ec07b545EddE332A47C2F75bbeb3`（"JPY / USD"・8 decimals・USD per JPY を返す）                        |


---

## 1. 方針

監査修正では、JPY/USD の `stalenessThreshold` を **30h（108,000秒）**、キャッシュ利用の猶予を **24h** とする。従来の72hから短縮し、操作ごとに価格の利用期限を分ける。

- 30h以上では、新規借入・債務増加・担保引出・通常償還・新たな恒久shutdown判定を止める。恒久shutdown前の `closeTrove` も全額返済と担保引出を組み合わせるため、この制限に含む。
- 返済・担保追加だけの調整は価格取得を要しない。権限、最低債務、恒久shutdown後の制限は維持する。
- 清算は他の価格入力が有効な場合に限り、JPY価格の経過時間が54h未満まで継続できる。
- 新しいJPY更新を取得した後、累積利息を含むTCRを再計算し、SCR未満なら恒久shutdownを許可する。

値の正本は [Parameters](../../../Parameters.md) `PRM-ORACLE-001/006/008`、動作は [Oracle](../../product/spec/Oracle.md) `ORCL-SEC-005`。24hの追加猶予は検証対象の方針であり、最適性や本番リスク承認を意味しない。

---

## 2. 前提：heartbeat と staleness threshold は別物

決定対象を取り違えないため、2 つの「期間」を区別する。

- **heartbeat（24h）** … Chainlink 側が固定する「価格が無変動でも更新することを期待する」周期。障害時の更新を保証するものではない。**外部仕様で、我々は変更できない**。
- **staleness threshold（本書の決定対象）** … 我々が PriceFeed に設定する「`updatedAt` が何秒前まで健全とみなすか」のオンチェーン閾値。

判定式（`MainnetPriceFeedBase`）は `block.timestamp - updatedAt < stalenessThreshold`。**strict `<`**（閾値ちょうど経過で stale）で、曜日・祝日カレンダーを持たない。

週末・祝日の休場と、オンチェーンの更新停止は区別する。§3の観測では休場中も約24hごとに更新されており、72h近い無更新を通常の週末動作とは扱わない。

---

## 3. 実測根拠：FX 休場と無関係に 24h ごとに更新される

閾値は「FX 休場中にフィードが実際にどれだけ古くなりうるか」の実測で決める。唯一の懸念は「クリスマス・正月の長期 FX 休場で 24h の keepalive が途切れ、長時間 sticky に古くなるのではないか」だった。mainnet の Chainlink を直接実測してこれを否定した。

**検証対象と手法（再現可能）**

- 対象 proxy `0xBcE206caE7f0ec07b545EddE332A47C2F75bbeb3`（"JPY / USD"・8 decimals）の背後の aggregator を直接読む。phase 5 aggregator `0xA0B5260BDfD1011C4bcdc7A099C75BFf6340B38C`（2024-06〜現在）、phase 4 aggregator `0x01A1F73b1f4726EB6EB189FFA5CBB91AF8E14025`（〜2024）。
- 各 aggregator の `AnswerUpdated` イベントを**全件取得**し、`updatedAt`（実際に価格がオンチェーンへ posting された時刻）の**連続差分 ＝ フィードが古くなりうる最大時間**を算出する。archive 対応 RPC で 2026-06-17 に直接実測。

### 3.1 対象期間のスキャン

phase 5 を稼働開始（2024-06-28）から最新まで連続スキャンした。


| 範囲                                 | 更新数     | 最大更新間隔     | 25h 超   | 48h 超   |
| ---------------------------------- | ------- | ---------- | ------- | ------- |
| 2024-06-28 〜 2026-06-16（約 1.9 年連続） | 約 6,871 | **24.02h** | **0 件** | **0 件** |


最大 gap の上位はすべて ~24.02h で、特定の季節・曜日に偏らない（例：`2026-06-05 12:54→06-06 12:55`、`2025-09-05→09-06`、`2025-03-14→03-15`、いずれも 24.02h）。取引日は価格変動に応じ sub-hourly で更新され、無更新が続くのは FX 休場中のみ。その休場中も 24h ごとに最後の健全レートが posting され続け、多日サイレンスは発生しない。

### 3.2 年末年始シーズン別（懸念の直接検証）

FX が 3 連休（土日月）でクローズする最悪条件を含め、過去 5 シーズンの年末年始を個別に実測した。


| シーズン    | aggregator | 更新数 | 最大 gap | 25h 超 | 元日 `12/31→1/1` |
| ------- | ---------- | --- | ------ | ----- | -------------- |
| 2021/22 | phase 4    | 38  | 24.03h | 0     | 24.01h         |
| 2022/23 | phase 4    | 445 | 24.01h | 0     | ~24.0h         |
| 2023/24 | phase 4    | 193 | 24.01h | 0     | 24.01h         |
| 2024/25 | phase 5    | 184 | 24.01h | 0     | 24.01h         |
| 2025/26 | phase 5    | 94  | 24.01h | 0     | 24.01h         |


- **クリスマス（12/24→25）・元日（12/31→1/1）・3 連休のいずれでも、24h 間隔の keepalive が一度も途切れていない。** 例：`2023-12-30 16:14 → 12-31 16:15 → 2024-01-01 16:15`（各 24.01h）。market の開閉と無関係に heartbeat が発火する。
- 全 5 シーズンで 25h 超ゼロ。「年末年始の長期休場で多日サイレンスが起きる」という懸念は実データで否定された。

対象期間の最大値は約24hだった。phase 5の連続スキャンでは24.02h、年末年始の個別観測では最大24.03hであり、将来の障害時にこれを超えないという意味ではない。

## 4. 30hの制限と24hの清算猶予

§3の実測期間では最大更新間隔は約24hだった。30hは通常の更新間隔に余裕を持たせつつ、更新欠落後の追加借入リスクを抑える。観測値は将来の更新間隔やFX変動幅の上限を保証しない。

30〜54hに清算を続けると、円高では清算漏れ、円安では健全なTroveの誤清算が起こり得る。一方、30hで清算も止めると、担保価格の下落中に債務を回収できず担保不足が増える可能性がある。両方向のFX変動をMCR付近で比較し、清算停止時の損失も評価する。恒久shutdownを待つ間の利息増加とurgent redemptionの遅延も対象とする。

## 5. 猶予の起点と回復

全active branchで単一の `JpyUsdRateProvider` を使う。`jpyFrozenSince` は初回障害観測と `lastGoodJpyUpdatedAt + 30h` の早い方で、最後のアクセスから24hを再開始してはならない。したがって、stalenessだけが原因なら54hちょうどで猶予が切れる。無効値などを先に検出した場合は、より早く切れる。

猶予中も担保・peg・canonical・backingの有効性検査を維持する。オラクル障害によるpauseは回復可能で、TCR/SCRによる恒久shutdownとは異なる。新しい有効な価格が戻れば清算は再開できるが、借入等のpause解除にはOwnerの検証付きresumeが必要。30hの経過時間制限だけではpauseを立てないため、新しいJPY更新でその制限は自動的に解除される。

運用手順は [Mainnet Deploy Env Freeze Runbook](../gates/Mainnet-Deploy-Env-Freeze-Runbook.md) §3.1.1 を参照する。

## 6. リスクと前提

- **外部依存**：Chainlink の heartbeat 変更・feed deprecate / migration は外部要因として残る。`data.chain.link` と on-chain `updatedAt` の監視で早期検知する。
- **監視即応が前提**：フィード直接監視と source 差替の即応運用を伴う。
- **二次情報の扱い**：deviation threshold ≈ 0.15% は公開データページ由来の参考値（原文未取得）。本決定はこれに依存せず、一次情報（オンチェーン実測の 24h keepalive）に基づく。実測挙動（取引日 sub-hourly・休場日 24h 間隔）はこの値と整合する。
