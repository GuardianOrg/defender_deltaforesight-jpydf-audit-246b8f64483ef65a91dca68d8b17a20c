# JPY DeFi Deploy Configuration Note

> **Positioning**: defines the Day-1 shape that `DeployLiquity2.s.sol` and the deploy manifest must produce. Collateral and risk parameters remain canonical in `Parameters.md`; contract requirements remain under `spec/`.

---

## 0. One-Line Summary

The Day-1 manifest emits **8 branches in a fixed order**. Only Branches 0–1 (`dwstETH / dUSDC`) bind an Underlying and production PriceFeed. Branches 2–7 (`dETH / dUSD-A / dBTC / dUSD-B / dJPY / dJGB`) are inert. `DF_BRIDGE_ADMIN` is a Safe or Timelock contract on mainnet and starts with zero bridge minters.

## 2. Deployment Modes

| `DEPLOYMENT_MODE` | Role | Manifest | Main use |
| --- | --- | --- | --- |
| `complete` | Deploy JPYdfToken, core, governance, and branches together | full manifest | Normal deploy |
| `jpydf-only` | Deploy only JPYdfToken | `{"jpydfToken": ...}` | Fix / pre-check CREATE2 token address |
| `use-existing-jpydf` | Verify an existing JPYdfToken and deploy core onward | full manifest | Main deploy after fixing token address first |

`use-existing-jpydf` requires the target token to have `totalSupply == 0`, `collateralRegistryAddress == 0`, and `owner == deployer`. It is not a mode for reusing an already minted or registry-configured token.

## 4. Day-1 Branch Shape

The current `complete` mode emits `NUM_DF_BRANCHES = 8` in a fixed order, with only `NUM_DF_ACTIVE_BRANCHES = 2` (indices 0–1) using active wiring and indices 2–7 marked `RESERVED`. Active branches finalize their Core risk parameters at deployment with `riskParamsFinalizer = address(0)` and `riskParamsFinalized = true`. Reserved branches deploy with `riskParamsFinalizer = DF_TIMELOCK` and `riskParamsFinalized = false`, and may finalize those parameters only once through the atomic ceremony in the Japanese [Inert Branch Activation Gate](../../../jp/protocol/operations/activation-gates/Inert-Branch-Activation-Gate.md).

| Index | dToken / Underlying | State | Deploy expectation |
| ---: | --- | --- | --- |
| 0 | `dwstETH / wstETH` | borrowable; prioritized ETH branch | dToken + Vault + `ORCL-FR-015` composite PriceFeed (`DFWstETHPriceFeed`) + CollateralYieldZapper (native-ETH staking route via `DF_ZAPPER_EXPECTED_STETH_0`); no Day-1 Strategy; initial JPY 35m cap |
| 1 | `dUSDC / USDC` | borrowable | dToken + Vault + Aave + Morpho Vault V2 Strategies + PriceFeedProxy + CollateralYieldZapper |
| 2 | `dETH / TBD` | reserved wiring | dToken cap 0, no Underlying, placeholder PriceFeed, no Strategy or CollateralYieldZapper, risk parameters unfinalized |
| 3 | `dUSD-A / TBD` | reserved wiring | same |
| 4 | `dBTC / TBD` | reserved wiring | same |
| 5 | `dUSD-B / TBD` | reserved wiring | same |
| 6 | `dJPY / TBD` | reserved wiring | same |
| 7 | `dJGB / TBD` | reserved wiring | same |

Day-1 liquidity / zap routes are limited to JPYdf/USDC Uniswap v4. Borrowable collateral is limited to cap-positive dwstETH and dUSDC. Branches 2–7 are non-operable reserved metadata in frontend and ops surfaces.

`YieldLayerProxyDeployer` initializes every active and reserved dToken at cap 0. After `AddressesRegistry.setAddresses`, the deployer binds each dToken to that registry through `setRiskParamsRegistry` and verifies the reference in its readback. Governance preparation keeps caps at zero; issuance opens only after risk finalization and the separately approved controlled initialization.

Sepolia Branch 1 is fixed to the [Aave V3 Sepolia address book](https://github.com/aave-dao/aave-address-book/blob/main/src/AaveV3Sepolia.sol) USDC Underlying at `0x94a9D9AC8a22534E3FaCa9F4e7F2E2cf85d5E4C8`. It is funded through the Aave Faucet at `0xC959483DBa39aa9E78757139af0e9a2EDEb3f42D`; the deploy script does not deploy a mintable substitute on Sepolia. Local Anvil retains a self-contained six-decimal local USDC for regression tests.

## 5. Manifest Contract

Current consumers read only the `deployment-manifest.json` generated by the deploy script. `deployment-manifest.json` is a git-ignored artifact; old local schema remnants and hand-written address snapshots must not be treated as current manifests.

Required top-level fields:

- `constants`
- `collateralRegistry`
- `jpydfToken`
- `bridgeAdmin`
- `bridgeMinterCount`
- `proposedBridgeMinter`
- `launchEvidence`
- `hintHelpers`
- `multiTroveGetter`
- `liquidationCandidateGetter`
- `debtInFrontHelper`
- `redemptionHelper`
- `branches[]`
  - `riskParamsFinalizer`
  - `riskParamsFinalized`
- `governance`

Only with DF wiring:

- `dfYield[]`
  - `dToken`
  - `collateralVault`
  - `collateralYieldZapper`
  - `stEthToken`
  - `lidoReferral`
  - `treasury`
  - `strategies[]`
    - `strategy`
    - `strategyKind`
    - `strategyWeightBps`
    - `strategyCap`
  - `underlying`

`branches[].riskParamsFinalizer` and `riskParamsFinalized` emit the exact `AddressesRegistry` getter readbacks. Deploy-tail verification fails unless Branches 0–1 read `address(0)` / `true` and Branches 2–7 read the common `DF_TIMELOCK` / `false`. A later activation does not rewrite the deployment manifest. Instead, the parameter Manifest, Timelock execution record, and block-stamped current-state Evidence track the one-way transition to `true` and verify that the BorrowerOperations / TroveManager consumer copies match all six Registry values.

`dfYield.length` must equal `branches.length`. `stEthToken` is the deployed Zapper's constructor-fixed getter value, while `lidoReferral` is the getter snapshot at manifest generation time; branches without the route output zero for both. A Timelock update does not rewrite the existing deployment manifest: separate current-state evidence records `DF_ZAPPER_EXPECTED_LIDO_REFERRAL_0`, the update event, and the getter readback. Reserved branches output `underlying == address(0)`, `strategies.length == 0`, and `collateralYieldZapper == address(0)`. If an active branch explicitly sets `DF_STRATEGY_KIND_i=none`, it outputs `strategies.length == 0`, while Underlying / CollateralYieldZapper / PriceFeed remain active as usual. Branches with one or more Strategies use `strategies[]` as the only manifest source. Fresh deploy does not emit legacy top-level `strategy` / `strategyKind` / `strategyWeightBps` / `strategyCap`.

## 6. Deploy Env Checklist

### Base deploy

| Env / option | Requirement | Meaning |
| --- | --- | --- |
| `DEPLOYER` | required | Public deployer address only; private keys are rejected. Sign through `./deploy` with Ledger (default), `--account` (Foundry keystore), `--aws` (AWS KMS), `--trezor`, or `--unlocked` for local/fork use only. |
| `DEPLOYMENT_MODE` | default `complete` | `complete` / `jpydf-only` / `use-existing-jpydf` |
| `SALT` | optional | CREATE2 salt. Defaults to `block.timestamp` when omitted |
| `DF_BRIDGE_ADMIN` | required on mainnet / Sepolia / unknown non-mainnet | Bridge-ready dormant extension holder for `JpydfToken`. Mainnet must use a Safe / Timelock contract, not the deployer. |
| `DF_ENABLE_MAINNET_DTOKEN_WIRING` | mainnet Day-1 only | Switches mainnet `complete` to 8-branch dToken wiring |
| `DF_ALLOW_TEST_WIRING` | unknown non-mainnet only | Allows local/test wiring on unrecognized chains |

Bool envs treat only `true` / `1` / `yes` as enabled; `false` / `0` / unset are disabled.

### DF dToken wiring

| Env | Requirement | Meaning |
| --- | --- | --- |
| `DF_TREASURY` | required for DF wiring | Initial Vault treasury |
| `DF_INTEREST_ROUTER_RECIPIENT` | required for DF wiring | PIL recipient |
| `DF_INTEREST_ROUTER_OWNER` | required for DF wiring | InterestRouterForwarder owner |
| `DF_JPY_USD_FEED` | required for mainnet DF wiring | Shared JPY/USD feed for all active branches |

| `DF_ZAPPER_EXPECTED_STETH_0`   | required for mainnet / Sepolia Branch 0                      | stETH used by the native-ETH route. Sepolia is fixed to Lido stETH `0x3e3FE7dBc6B4C189E7128855dD526361c49b40Af`                                                                                                                                                                                                                                                                         |
| `DF_ZAPPER_LIDO_REFERRAL_0`    | required for production mainnet Branch 0; optional elsewhere | Protocol-designated initial referral address recorded by every Lido `submit` on the native-ETH route (Lido Rewards Share attribution). The general contract permits leaving it unset / `address(0)` to disable attribution, but production mainnet requires an exact match with `config/day1-branch-manifest.json` before deployment in both the CLI and Forge script, then verifies the generated manifest and `lidoReferral()` through preflight. After deployment only `DF_TIMELOCK` can update it through `setLidoReferral`, evidenced by the update event and a `lidoReferral()` readback. |
| `DF_ZAPPER_EXPECTED_LIDO_REFERRAL_0` | optional | Expected referral at preflight time. Kept separate from the initial deploy value; used for current-state readback after Timelock updates. |
| `DF_TIMELOCK` | required outside local Anvil | Common Timelock contract fixed in the constructor as both `CollateralYieldZapper.lidoReferralManager` and the `AddressesRegistry.riskParamsFinalizer` for Branches 2–7. | `DF_COLL_USD_FEED_0..1` | required for mainnet active branches | stETH/USD (Branch 0 dwstETH market leg) / USDC/USD |
| `DF_COLL_USD_STALENESS_0..1` | required for mainnet active branches | active-branch collateral/USD thresholds |
| `DF_STRATEGY_KIND[_i]` | required for active branches | `aave` / `erc4626` / `morpho-v2` / `sky-susds` / `none` (the `lido` / `etherfi-weeth` kinds were dropped with the wstETH branch swap); adoption follows [Strategy Selection Policy](../../protocol/operations/policies/Strategy-Selection-Policy.md) |
| `DF_STRATEGY_WEIGHT_BPS[_i]` | required for active branches | Vault strategy weight. Must be `0` for `none` |
| `DF_STRATEGY_CAP[_i]` | required for active branches | Strategy cap. Must be `0` for `none` |
| `DF_STRATEGY_COUNT_i` | optional | Number of Strategies to auto-deploy/register for a branch. If absent, the script reads the single-Strategy env form |
| strategy-kind specific env | required by kind | Aave / ERC4626 / MorphoV2 / Sky addresses (the retired Lido / Etherfi env readers were removed with their kinds) |

`DF_STRATEGY_KIND_i=aave` requires `DF_STRATEGY_AAVE_POOL_i` and `DF_STRATEGY_AAVE_ATOKEN_i` on mainnet, explicitly pointing to the Aave V3 Ethereum production Pool and the aToken corresponding to the branch Underlying. On Sepolia, the deploy script fail-closes the dUSDC Underlying, Aave V3 Pool `0x6Ae43d3271ff6888e7Fc43Fd7321a503ff738951`, and aUSDC `0x16dA4541aD1807f4443d92D26044C1147406EB80` to the Aave address-book values and verifies live Aave Sepolia supply / withdraw. Only local Anvil and explicitly allowed other test chains use the production Strategy implementation with a local Aave parity venue. Day-1 freeze values and fork dry-run procedure are in [`Mainnet-Deploy-Env-Freeze-Runbook.md`](../../protocol/launch/gates/Mainnet-Deploy-Env-Freeze-Runbook.md).

`DF_STRATEGY_KIND_i=none` explicitly means "no venue"; it is not an escape hatch that hides a missed deploy. `DeployLiquity2` requires `DF_STRATEGY_WEIGHT_BPS_i == 0`, `DF_STRATEGY_CAP_i == 0`, and zero registered Vault strategies for `none` branches. Handover / verify / local accept helpers compare manifest `strategies[]` length with the Vault registered Strategy count and require `strategies.length == 0` for `none` branches.

dwstETH (Branch 0) uses `DF_STRATEGY_KIND_0=none` with weight/cap 0 and zero registered Strategies. Native wstETH staking appreciation remains borrower collateral value; any future external Strategy requires a separate activation package. dUSDC (Branch 1) uses `aave` + `morpho-v2`. Inert Branches 2–7 also use no Strategy. `withdrawDelay` and `bufferTargetBps` are canonical in [Parameters](../../Parameters.md) and must be re-derived before enabling a future asynchronous Strategy.

For a multi-Strategy branch, set `DF_STRATEGY_COUNT_i=N` and specify each
Strategy with `DF_STRATEGY_KIND_i_j` / `DF_STRATEGY_WEIGHT_BPS_i_j` /
`DF_STRATEGY_CAP_i_j` plus kind-specific `..._i_j` env keys. Example: dUSDC
branch index 1 with Aave + Morpho Vault V2 uses `DF_STRATEGY_COUNT_1=2`,
`DF_STRATEGY_KIND_1_0=aave`, `DF_STRATEGY_KIND_1_1=morpho-v2`, and
`DF_STRATEGY_MORPHOV2_VAULT_1_1` with the frozen weights. Do not put `none` inside the array form;
`none` only represents a single branch with no Strategy.

Strategy kind selection follows [Strategy requirements](../../protocol/product/spec/strategies/Strategy.md) §2.2.
ERC-4626 venues where `asset() == underlying` use `erc4626`. Asset-transforming
venues require dedicated Strategies. The current implementation includes
`sky-susds` for `USDC -> USDS -> sUSDS` and `morpho-v2` for Morpho Vaults V2
(whose `max*` views are zero by design and thus unfit for `erc4626`).

Additional kind-specific env:

| kind | Required env |
| --- | --- |
| `erc4626` | `DF_STRATEGY_ERC4626_VAULT_i` |
| `morpho-v2` | `DF_STRATEGY_MORPHOV2_VAULT_i` |
| `sky-susds` | `DF_STRATEGY_SKY_USDS_i`, `DF_STRATEGY_SKY_SUSDS_VAULT_i`, `DF_STRATEGY_SKY_USDC_USDS_PSM_WRAPPER_i`, `DF_STRATEGY_SKY_MAX_CONVERSION_LOSS_BPS_i`; the deploy script creates a concrete converter bound immutably to the wrapper |

`DeployLiquity2` fails fast when a kind-specific external venue address
(Aave Pool / aToken, ERC-4626 vault, Morpho Vaults V2 vault,
or Sky USDS / sUSDS / converter) is `address(0)` or has no
contract code. Optional addresses such as referrals are outside this
contract-only preflight.

Optional kind-specific env:

| kind | Optional env |
| --- | --- |
| `morpho-v2` | `DF_STRATEGY_MORPHOV2_MAX_PENALTY_BPS_i` (default `200`; values above 200 bps are rejected) |

`CollateralVault` can register multiple Strategies for one branch and split
allocation by `weightBps`, such as the Branch 1 Aave + Morpho Vault V2 set. `DeployLiquity2`
supports initial multi-Strategy registration through the `DF_STRATEGY_COUNT_i`
array form. Deploy-tail verification checks the Vault registered Strategy count,
primary strategy, each Strategy `vault()` / `underlying()`, and nonzero total
weight. Governance prepare / verify / accept helpers use the live Vault
registered Strategy list, so secondary Strategies receive the same owner /
upgrader handover as the primary Strategy.

Handover / activation separately require `PrepareDFGovernanceHandover.s.sol` and `VerifyDFGovernanceHandover.s.sol` env such as `DF_TIMELOCK`, `DF_GUARDIAN`, `DF_ALLOCATOR`, `DF_WRITEOFF`, `DF_PRICE_FEED_OWNER`, `DF_STRATEGY_OWNER`, `DF_STRATEGY_UPGRADER`, and per-branch `DF_DTOKEN_CAP_i`.

### 6.1 Aave Faucet USDC / live Aave Strategy Sepolia smoke

After a fresh Sepolia complete deploy, run `PrepareDFGovernanceHandover` to activate the approved dUSDC cap. Fund the public address holding the Vault `ALLOCATOR_ROLE` (normally `DF_ALLOCATOR`) by calling `mint(token, to, amount)` on the Aave Faucet at `0xC959483DBa39aa9E78757139af0e9a2EDEb3f42D`, pass that public address as `DEPLOYER`, then run. Do not run the smoke against the cap-0 post-deploy state:

```bash
DEPLOYER=0x... \
DF_SEPOLIA_USDC_SMOKE_AMOUNT=1000000 \
forge script VerifySepoliaAaveUsdc \
  --rpc-url "$SEPOLIA_RPC_URL" \
  --broadcast
```

The smoke requires a fresh dUSDC branch and round-trips Aave Faucet USDC approval/deposit, 6-to-18 decimal conversion, Vault allocation, production `AaveV3Strategy` supply / withdraw against the live Aave V3 Sepolia Pool, aUSDC accounting, `sendToVault`, and dUSDC redemption. Before execution it checks the fixed Underlying / Pool / aUSDC addresses, aUSDC Underlying, and Faucet mintable state. It finally checks that the tester USDC balance, dUSDC total supply, Vault buffer, Strategy principal / estimated value, and aToken scaled balance return to their initial state.

## 7. Deploy-Tail Verification

With DF wiring, the script fail-fast checks the following at the end:

- registry token / troveManager match branch contracts
- `PriceFeedProxy.borrowerOperations()` matches `AddressesRegistry.priceFeed()`
- `fetchPrice()` / `fetchRedemptionPrice()` are nonzero / nonmax / nonfailed
- core collateral is dToken
- dToken and Vault mutually match
- Vault treasury equals `DF_TREASURY`
- active branch cap is 0 and backingRatio is `1e18`
- active feed source references the branch Vault
- if active Strategies exist, the primary strategy matches Vault slot 0 and each registered Strategy matches Vault / underlying; active branches with `DF_STRATEGY_KIND_i=none` have `dfYield[i].strategies.length == 0`, zero registered Vault strategies, and `totalWeightBps == 0`
- active CollateralYieldZapper matches Vault / dToken / BO / JPYdf / underlying
- inert branches have no underlying, cap 0, and no CollateralYieldZapper
- every branch's `interestRouter` is the single `InterestRouterForwarder`, with token / recipient / owner / pendingOwner matching expectations

This verification protects non-mainnet DF wiring and mainnet opt-in DF wiring quality, but it is not a substitute for freezing mainnet real-value env and running a fork dry-run.
