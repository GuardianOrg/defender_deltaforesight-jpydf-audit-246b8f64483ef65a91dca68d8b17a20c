# Contract Business Catalog

## 0. Positioning of This Document

This is a catalog intended to let business-side and non-Solidity reviewers quickly grasp "what each contract does" in a short time.

- **Scope**: The major contracts among the production Solidity sources in `contracts/src` that are relevant to Day-1 understanding of the product / audit / operations.
- **Non-goals**: Comprehensive coverage of function-level specs, parameter values, audit findings, or implementation diffs.
- **Source of truth**: For strict specifications, [`Product-Overview.md`](../../protocol/product/Product-Overview.md), [`Parameters.md`](../../Parameters.md), and each [`protocol/product/spec/`](../../protocol/product/spec/) are authoritative. Where this document and a spec disagree, the spec governs.
- **How to read**: First read the overview in §1, then look at the table for your area of interest. For audit estimates and nSLOC, refer to [`Contract-Audit-Scope-And-nSLOC.md`](Contract-Audit-Scope-And-nSLOC.md).

## 1. Overview

JPYdf v2 is broadly composed of the following 5 layers.

| Layer | Business role | Main contracts |
| --- | --- | --- |
| Liquity v2 Core | The basic system where users deposit collateral to borrow JPYdf, get liquidated / redeemed, and where interest accrues | `BorrowerOperations`, `TroveManager`, `ActivePool`, `DFStabilityPool`, `CollateralRegistry` |
| JPYdf / dToken / Vault | Converts real-world assets and yield-bearing assets into an 18-decimals collateral representation that Liquity Core can handle, and custodies, manages, and redeems them | `JpydfToken`, `DToken`, `CollateralVault`, `Strategies/*` |
| Oracle | Passes collateral prices to Core denominated in JPY. Handles feed replacement and placeholder branches | `PriceFeedProxy`, `DFPriceFeedBase`, per-collateral price feeds |
| Zapper / Route | Bundles user operations into a single transaction. Day-1 covers the generic Zapper and Uniswap v4 final leg | `CollateralYieldZapper`, `UniV4Exchange` |
| Interest / PIL / Operations | Collects the interest share and operating yield generated by Core into the Day-1 receiving entity, and gates PIL liquidity incentives for production operations | `InterestRouterForwarder`, `PILAllocator`, `UniV4MerklInitiative`, strategy reward sweep |

### 1.1 Reading Audit Scope vs Day-1 Activation

"Included in the audit scope" does not mean "user-facing / funded / active on Day-1." The Day-1 audit scope intentionally includes the production `contracts/src` surfaces that can affect funds, accounting, authorization, routes, or incentives. Actual activation is narrower and is gated by the deploy manifest, preflight checks, Safe / Timelock approval, fork evidence, and strategy-selection evidence.

| Status | Business reading | Examples |
| --- | --- | --- |
| Day-1 active / planned active | Expected for production once the launch package gate is satisfied | Core, `JpydfToken`, `DToken`, `CollateralVault`, active price feeds, `CollateralYieldZapper`, Aave, and Morpho Vaults V2 via `MorphoV2Strategy` |
| Audited but gated | Code exists and is reviewed, but is not exposed to production flows until route / PIL / branch / manifest gates pass | `UniV4Exchange`, `PILAllocator`, `UniV4MerklInitiative`, bridge-ready dormant minter surface, cap-0 branch surfaces |
| Implemented optional Strategy | Production source remains in scope, but it is not part of the expected launch manifest | `SkyUsdcSUsdsStrategy`, non-Morpho ERC-4626 venues, branch 2+ strategies |
| Archived (previously audited) | Retired from the active Day-1 scope; moves under `contracts/src/Strategies/archive/` and is preserved as an audited artifact, never deployed, registered, or allocated | `LidoStrategy`, `EtherfiWeETHStrategy` / `WeETHWithdrawAdapter` |
| Day-2 / not implemented | Outside Day-1 contract audit scope. Requires a separate PR and audit package | `Treasury.sol`, SP additional reward distributor, referral distributors, active bridge adapter |
| Removed / absent | Fresh deploy keeps no compatibility shims | Curve, Balancer, Uniswap v3 routes, flash-close, collateral-funded repay, Multiply, direct non-USDC JPYdf pools |

## 2. Core: The Main Body of Borrowing, Liquidation, and Redemption

This layer preserves the Liquity v2-derived behavior as much as possible. From a business standpoint, you can understand it as "the protocol body for borrowing JPYdf."

| Contract | What it does | Business meaning | Main risks / points to check |
| --- | --- | --- | --- |
| `BorrowerOperations` | The entry point for user Trove operations. Receives open / add collateral / withdraw collateral / borrow / repay / close, etc. | The entrance to the borrowing UX. The place where users deposit collateral and receive JPYdf | manager permissions, fee, Trove state transitions, the recipient when going through the Zapper |
| `TroveManager` | Manages the debt / collateral / stake / liquidation state of each Trove | The borrowing-position ledger. The source for calculating liquidatability and collateral ratio | debt accounting, stake redistribution, the boundary between liquidation / redemption |
| `ActivePool` | The pool holding the aggregate collateral and debt of active Troves | The place where not-yet-liquidated collateral and debt are aggregated | aggregate accounting, approval, accrual of the interest share |
| `DefaultPool` | After liquidation, temporarily holds collateral / debt awaiting redistribution | The relay until liquidation profit/loss is redistributed to other Troves | redistribution accounting |
| `CollSurplusPool` | The pool from which users claim collateral left over after liquidation or redemption | The custody place for surplus collateral that must be returned to users | claim permissions, surplus calculation |
| `DFStabilityPool` | The pool where JPYdf depositors absorb liquidations and earn collateral rewards. The DF version adds a same-block withdrawal guard | The safety valve for JPYdf. The primary backstop during liquidation | withdrawal timing guard, deposit accounting, reward distribution |
| `CollateralRegistry` | Holds the list of multiple collateral branches and the entry point for redemption / urgent redemption | The branch catalog. Manages which collateral is active and where redemptions are directed | branch index, redemption ordering, shutdown boundary |
| `SortedTroves` | An auxiliary structure that orders Troves by interest rate or ICR | Improves the efficiency of redemption / liquidation / UI display | hint, ordering, edge cases |
| `RedemptionHelper` | Assists in the actual processing of redemptions | The core helper for the process of returning JPYdf to receive collateral | min receive, branch shutdown, skip conditions |
| `HintHelpers` / `MultiTroveGetter` | Read helpers for UI / Bots to efficiently search Troves | Search assistance for the frontend / liquidators | being read-only, pagination |
| `JPYdfTroveNFT` / `JPYdfMetadataNFT` | Represents Trove ownership as an NFT and returns tokenURI metadata | Display of Trove ownership. Visible to wallets / explorers / UIs | ownership authorization, accuracy of metadata display |

## 3. JPY DeFi / dToken / Vault: The Proprietary Business Layer

This layer carries strong JPYdf v2 originality. It is the custody / accounting / yield integration for loading real-world assets and yield-bearing assets onto Core.

| Contract | What it does | Business meaning | Main risks / points to check |
| --- | --- | --- | --- |
| `JpydfToken` | The debt token that Core mints / burns. On Day-1 it holds dormant bridge readiness with bridge minter 0 | The JPY-denominated stablecoin that users borrow. Separates Core issuance from future bridge issuance | Core mint permissions, bridge minter timelock, Day-1 minter 0, permit domain |
| `DToken` | An ERC20 that converts an Underlying into an 18-decimals collateral token. Only the Vault can mint / burn it | A collateral representation that is easy for Liquity Core to handle. E.g., dToken-izing wstETH or USDC | Vault binding, cap, underlying allowlist, decimals conversion |
| `CollateralVault` | Custodies the Underlying and manages dToken mint / redeem, buffer, delayed withdrawal, and strategy allocation | The main body of real-world asset custody and operating accounting | 1:1 backing, buffer / queue, strategy loss, writeoff, upgrade boundary |
| `InterestRouterForwarder` | Forwards the interest share received from the ActivePool to the current recipient | A simple forwarder to the Day-1 PIL / Treasury receiving entity | recipient permissions, route keeper, stuck funds |
| `PILAllocator` | Distributes the PIL portion of borrowing interest to registered initiatives by admin weight | A deploy-ready / evidence-ready incentive allocator for Day-1. Active routing is a separate activation gate | initiative registration, weight sum, bounded loops, carry-over, pause / guardian |
| `UniV4MerklInitiative` | Uses JPYdf received from `PILAllocator` to create Merkl campaigns | A candidate recipient for JPYdf/USDC Uniswap v4 liquidity incentives | Merkl trust boundary, campaign threshold, epoch alignment, allowance hygiene |
| `LiquidationCandidateGetter` | A read helper for liquidation Bots / frontend to fetch liquidation candidates page by page | Operational assistance that improves liquidator search efficiency | invalid branch, bounded scan, zombie handling |

## 4. Strategy: Moving Assets from the Vault to External Yield Sources

A Strategy is "an adapter for depositing a portion of the Underlying custodied by the Vault into an external protocol to earn yield." The Day-1 business risk lies in keeping external protocol risk and Vault accounting from intermingling. The expected Day-1 manifest is Branch 0 dwstETH: Aave only (aEthwstETH), and Branch 1 dUSDC: Aave + Morpho Vault V2 (`MorphoV2Strategy`); Branches 2–7 have no Strategy. Lido and Etherfi are retired from the Day-1 deploy surface and move to the archive tree as previously audited artifacts; Sky remains outside launch-active status until a separate scope change. Current venue adoption follows [Strategy Selection Policy](../../protocol/operations/policies/Strategy-Selection-Policy.md).

| Contract | What it does | Business meaning | Main risks / points to check |
| --- | --- | --- | --- |
| `BaseStrategy` | Provides the common push model, principal accounting, owner / upgrader, and reward sweep | The standard operating rules for all strategies | onlyVault, principal tracking, emergency withdraw, upgrade authority |
| `AaveV3Strategy` | Supplies the Underlying to Aave V3 and holds an aToken position | A low-friction operating venue via Aave | aToken accounting, withdraw failure, Aave / Merkl reward |
| `ERC4626Strategy` | A generic adapter that deposits the Underlying into an ERC-4626 vault | Connects standard ERC-4626 vaults without venue-specific contracts; Morpho Vault V2 uses `MorphoV2Strategy` instead | share rounding, preview/convert assumptions, vault compatibility |
| `MorphoV2Strategy` | Deposits the Underlying into a Morpho Vaults V2 vault without relying on `max*` views, with fail-soft recovery and a bounded `forceDeallocate` penalty | The audited dedicated adapter for the Day-1 Branch 1 Morpho Vault V2 slot | curator/queue behavior, penalty bound (<= 200 bps), donation exclusion, share resync |
| `LidoStrategy` | Stakes WETH into Lido and handles asynchronous recovery through wstETH / the Withdrawal Queue | Archived (previously audited) | if an instance exists: pending withdrawal, claimable ETH, loss/writeoff, donation separation, recovery and unregister |
| `SkyUsdcSUsdsStrategy` | Converts the USDC of dUSDC into USDS / sUSDS to operate, and recovers in USDC | Implemented optional Strategy. Outside the expected Day-1 manifest; adoption requires separate activation / audit-scope confirmation | converter trust, USDS/sUSDS rate, min-out, idle USDS, ignoring donation |
| `EtherfiWeETHStrategy` | Converts branch WETH into Ether.fi eETH / weETH and recovers asynchronously via WithdrawRequestNFT | Archived (previously audited; retired from the Day-1 deploy surface with the wstETH branch swap) | pending NFT, claimable ETH, LRT/slashing/depeg, keeper, ignoring donation |

## 5. Oracle: Passing JPY-Denominated Prices to Core

The Oracle determines "whether the collateral is sufficient against the JPYdf debt." If the price feed is wrong, the borrowing cap, liquidation, and redemption are all affected.

| Contract | What it does | Business meaning | Main risks / points to check |
| --- | --- | --- | --- |
| `PriceFeedProxy` | The feed address fixed into Core. Replaces the backing source with a timelock | A safety valve to swap the oracle source without re-deploying Core | source replacement, smoke test, owner handover, no-renounce |
| `DFPriceFeedBase` | The DF common base that composes collateral/USD and USD/JPY to output a JPY-denominated price | The price conversion logic for JPYdf | stale price, invalid response, lastGoodPrice |
| `DFUSDCPriceFeed` / `DFWstETHPriceFeed` | JPY price feeds for Day-1 active collateral | Prices for dUSDC / dwstETH | depeg / wrapper rate, staleness, JPY freeze |
| `CompositePriceFeed` | Shared base for canonical-rate composition | Supports the active dwstETH feed | canonical rate, lastGoodPrice fallback |
| `PriceFeedPlaceholder` | A placeholder feed for inert branches | Makes accidental activation of unused branches less likely | not miswiring it to an active branch |
| `MainnetPriceFeedBase` | The upstream-derived feed base | A price-retrieval component that maintains base-parity. The non-deployed upstream WETH wrapper and the WSTETH / RETH collateral feeds have been removed | upstream parity, rate source |

## 6. Zapper / Route: Bundling User Operations

A Zapper is "a UX router that lets users operate in a safe order without having to understand multiple steps." On Day 1 the focus is open / add / withdraw / close-with-JPYdf; swap-backed close / Multiply do not exist in the ABI.

| Contract | What it does | Business meaning | Main risks / points to check |
| --- | --- | --- | --- |
| `BaseZapper` | Provides Trove manager permissions, receiver guard, and common helpers | The authorization foundation for Zapper operations | manager / receiver mismatch, owner vs automation |
| `AddRemoveManagers` | Manages a Trove's add manager / remove manager + receiver | The mechanism for delegating permissions to a cold wallet / bot / automation | scope of manager permissions, receiver settings |
| `LeftoversSweep` | A helper that returns tokens left over after Zapper / exchange operations | Prevention of stranded user assets | leftover accounting, unexpected residue |
| `CollateralYieldZapper` | Bundles Underlying deposit -> Vault -> dToken collateral -> Core operations into 1 tx | The primary user UX for dToken branches | allowance, leftover, min underlying, receiver, reentrancy |
| `UniV4Exchange` | The `IExchange` adapter for the JPYdf/USDC Uniswap v4 final leg | A target for future swap routes / evidence. Included in the Day-1 audit scope, but the user-facing route is gated | Universal Router / Permit2 allowance, pool key, hook policy, JPYdf->coll exact-output / coll->JPYdf exact-input |
| `V4RouterCodec` | The byte definitions for Universal Router / v4 action commands | The components of the commands the adapter passes to the v4 router | command byte correctness |

Candidate-specific `DFUSDTPriceFeed`, `DFWBTCPriceFeed`, `DFXAUTPriceFeed`, `sUSDSPriceFeed`, and `SkyUsdcSUsdsYieldZapper` sources are isolated under `contracts/src/**/archive/` and excluded from the official deploy path and active audit scope.

## 7. How to Read Interfaces / Libraries / Helpers

| Kind | Examples | Business handling |
| --- | --- | --- |
| Interface | `I*` files | Not implementations but a promise of ABI and meaning. In audits, viewed as interface consistency |
| Types | `TroveId`, `LatestTroveData`, `TroveChange`, etc. | Types for Core / frontend / helpers to share the same data shape |
| Math / Dependencies | `LiquityMath`, `Constants`, `SignedMath`, etc. | Parameters, calculations, and common guards. Values are cross-checked against `Parameters.md` |
| Vendored libraries | `contracts/lib/**` | Dependencies. Normally not included in the JPYdf audit nSLOC |

## 8. Things That "Do Not Exist" or Are "Not Yet User-Facing" on Day-1

| Item | Day-1 handling |
| --- | --- |
| Active bridge protocol / other-chain deployment | Not implemented or connected. `JpydfToken` holds only dormant readiness |
| Bridge for dToken / yield-bearing token | Out of the initial bridge scope |
| Curve / Balancer / Uniswap v3 routes | Not adopted. Not restored into production `src` |
| Direct JPYdf pools for USDT / USDS / WETH / XAUT, etc. | Not created under the Day-1 liquidity policy |
| JPYdf/USDC Uniswap v4 | The Day-1 standard liquidity. However, the user-facing wiring of `UniV4Exchange` is after route config / fork evidence / manifest gates |
| flash-close / collateral-funded repay / Multiply | Not present in the Day-1 contract ABI. If provided in the future, added as a new audited entrypoint |
| Sky Strategy activation / retired staking Strategies | `SkyUsdcSUsdsStrategy` exists in production source and audit scope but is outside the expected Day-1 manifest; do not register, allocate to, or expose it until a separate activation package. `LidoStrategy` / `EtherfiWeETHStrategy` are retired from the Day-1 deploy surface and move to the archive tree as previously audited artifacts |
| Day-2 Treasury / reward distributors | `Treasury.sol` / SP additional reward distributor / referral distributors are not Day-1 production implementations. Switching away from Safe retention requires a separate PR and audit package |
