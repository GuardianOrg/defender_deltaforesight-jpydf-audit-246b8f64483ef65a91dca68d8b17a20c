# AWS CDK Hosting Plan

This plan defines the implementation policy for hosting JPYdf's user app, ops dashboard, admin console, public stats JSON, and the liquidator / keeper backend on AWS CDK. The source of truth for the specification lives in each component spec / runbook; this document summarizes the placement on AWS, the separation of responsibilities, and the deploy order.

## 1. Scope

Day-1 hosting targets:

- `frontend/app`: public user app. Next.js static export (`next build` -> `out/`).
- `frontend/ops`: read-only ops / transparency dashboard. Vite static build
  (`vite build` -> `dist/`).
- Public stats JSON: the public health JSON generated by `frontend/ops`'s `export-stats`.
- `frontend/console`: restricted admin console. A Vite static build, but it is not
  published directly as a public static site.
- Hosted Anvil staging RPC: a chain for staging operation checks of the frontend / ops /
  deploy scripts. It is treated as a resettable dev chain rather than a testnet, and a UI
  indication that prevents it from being mistaken for production is required.
- `bots/liquidator`: Rust liquidator / keeper. On Day-1, dry-run / read-only
  evidence is run first, and live submission is a separate gate.
- Future ops workers: scheduled / manual workers such as `export-treasury-ledger` and
  `route-interest`.
- Mainnet fork stress rehearsal: GitHub Actions only invokes the dispatcher Lambda via
  OIDC, and execution of `contracts/utils/mainnet-fork-evidence.sh` using the archive RPC
  is kept on the CodeBuild side. Evidence for Safe / role holder calldata, frontend
  write-flow, admin console payload hash, and historical / synthetic stress scenarios is
  stored in S3.

Out of scope for Day-1 hosting:

- Productionizing subgraph self-hosting. Day-1 prioritizes a managed / hosted endpoint,
  and an AWS Graph Node is made an independent plan for Day-2 onward.
- Holding private keys within the admin console, or sending privileged transactions.
- Mock / fixture / stale completion within the user app.

## 3. Architecture Decision

CDK is adopted as the Day-1 standard implementation, but the hosting provider itself is
not made part of the protocol specification. The build artifact, deployment manifest,
stats JSON schema, admin auth boundary, and worker entrypoint are kept provider-neutral
so that future migration between Vercel / CloudFront, use or migration of Neon / RDS,
Render / ECS, and Better Stack / CloudWatch remain possible.

### Public user app

- Serve via Route 53 + ACM + CloudFront + a private S3 bucket.
- Do not use the S3 website endpoint. Use CloudFront Origin Access Control (OAC) and keep
  the regular S3 bucket origin private.
- Set the CloudFront viewer protocol policy to HTTPS redirect / HTTPS only.
- Manage HSTS, CSP, `X-Content-Type-Options`, `Referrer-Policy`, and the like via the
  CloudFront response headers policy.
- Attach a WAF web ACL, and apply managed rules, rate limit, and geo / bot policy to
  production after tuning them in staging.
- Treat `NEXT_PUBLIC_*` as public information. The RPC URL is not a secret but a public
  read key with a domain allowlist / rate cap / rotation owner.

### Hosted Anvil staging RPC

- `Jpydf-staging-HostedAnvil` is treated as a resettable dev chain on AWS. The default
  chainId is `31338`, so it is not confused with local Anvil (`31337`) or production /
  testnet.
- The stack is created only when there is an explicit opt-in of
  `JPYDF_HOSTED_ANVIL_ENABLED=true` in staging.
  Production synth rejects the hosted Anvil opt-in.
  The default synth emits only static hosting, and does not implicitly create Anvil even in production.
- The runtime is an Anvil container on ECS Fargate, and the public browser endpoint is the
  CloudFront HTTPS `AnvilRpcUrl` CloudFormation output. The frontend / ops pin this URL to
  the staging env, and on screen they always indicate that it is a staging / dev chain.
- Do not publish the ALB DNS as a supported endpoint. The ALB listener defaults to `403`,
  and forwards only requests that carry the CloudFront origin verification header to the
  Anvil target group. This is a routing guard, not an auth boundary, so do not place
  value-bearing assets or production secrets there.
- Assume that faucet / test accounts / reset / redeploy can be done freely. After a reset,
  recreate the contract manifest, the generated frontend env, and the subgraph / stats
  evidence.
- Hosted Anvil is not a substitute for a testnet; it is an environment for speeding up the
  pre-mainnet staging UX / deploy / rollback drills. For external integrator / audit
  evidence, separately attach testnet or mainnet fork evidence.

### Ops dashboard / public stats

- Separate the ops dashboard onto a different hostname / bucket / distribution from the
  user app.
- Place the public stats JSON in an S3 prefix separate from the dashboard bundle, or in a
  dedicated bucket. The JSON includes `generatedAt`, the source block, and the schema
  version.
- `publish-stats-s3` runs as an EventBridge scheduled ECS Fargate task. The initial CDK
  implementation uses `AWS::Events::Rule`, and the worker entrypoint / env contract does
  not change even if it is later moved to EventBridge Scheduler.
- Since `export-stats` is a script that outputs JSON to stdout / file, the S3 publish is
  done by the `publish-stats-s3` worker. Do not do a partial write directly to the stable
  key. Generate to a versioned key with `Content-Type: application/json`, a `Cache-Control`
  below the stale threshold, and schema/version metadata. The stable key reads the existing
  stats' `blockNumber` and ETag, and is updated monotonically with an `If-Match` /
  `If-None-Match` conditional PUT. On a condition conflict, reload; if the existing block is
  newer, exit as `skipped-stale-publish`.
- The generation worker logs the hash of the RPC / deployment manifest / generated
  bindings, and on failure does not overwrite the existing JSON with a mock.
- The stats publish explicitly specifies not only `--sse aws:kms` but also the
  `--kms-key-id` of the CDK stats bucket CMK. Objects written with the AWS managed
  `aws/s3` key cannot be decrypted under the CloudFront OAC + stack CMK policy, resulting
  in a 403 from the user app.
- The user app must not display stats stale / unavailable with the same appearance as a
  live value.
- The public ops UI displays a provider label such as `VITE_OPS_RPC_PROVIDER_LABEL`, and in
  production does not display the RPC host / full URL / key fragment / raw provider error /
  stack trace. Host displays such as localhost are limited to dev builds.

### Admin console

- Separate the admin console onto a different hostname, CloudFront / ALB, and auth / cache
  boundary from the user app / Ops. The browser-facing read-only RPC may be shared; in that
  case, manage it as a public credential observable from the public app / Ops, with every
  domain, aggregate quota, and rotation covered. RPC-key secrecy is not an Admin boundary.
- On Day-1, make ALB authentication (Cognito or an in-house OIDC IdP) + an ECS Fargate nginx
  static container the standard configuration. Even when placing CloudFront in front, do not
  create an origin path that can bypass ALB auth.
- The CloudFront front layer for the admin console is optional on Day-1; when adopted,
  separate the admin distribution / behavior from the public app, and pin a configuration
  that does not public-cache authenticated responses. The standard separately defines the
  cache policy as `CachingDisabled` and the origin request policy as forwarding all viewer
  headers / all cookies / all query strings, and applies them to the ALB auth behaviors (at
  least `/*` and `/oauth2/*`). Since the ALB auth cookie can be sharded, do not limit the
  cookie names. Make `Cache-Control: private, no-store`, HTTPS 443 end-to-end, and the
  unauthenticated / expired-session / cross-user cache drills required.
- When CloudFront is placed in front of the admin console, pin the handling of direct ALB
  access at the launch gate. If you use CloudFront-side WAF / response headers / logging /
  rate limit / noindex as the security boundary, configure the ALB to accept only requests
  via CloudFront. The implementation candidates are a network policy that allows only
  CloudFront-originated requests, a shared origin header verified at the ALB listener /
  backend, or WAF / host header constraints — any one of these or a combination — and the
  ALB DNS direct hit drill is required.
- Allow only via an IdP group with required MFA; a gate based on a shared password alone is
  not acceptable.
- Use `X-Robots-Tag: noindex`, HTML noindex, and `robots.txt` together.
- The console does not hold private keys. It is responsible up to Safe calldata export,
  target / value / function / args decode, and role / owner / manifest / chainId
  confirmation.
- When using the OIDC claims granted by the ALB for backend authorization, verify the
  signer / issuer / audience on the target side. Even when using it only as a static asset
  gate, restrict the target security group to traffic from the ALB only.

### Liquidator / keeper backend

- Run `bots/liquidator run` as an ECS Fargate service. At first, enable only block polling
  and evidence emission with a read-only / dry-run config.
- Place `state.path` on EFS. If it is later moved to DynamoDB / S3 object lock, pin the
  state schema and restart semantics in a separate PR.
- The CDK `BackendStack` converts the `starting liquidation catch cycle` log emitted by the
  liquidator into a `JPYdf/Backend` metric via a CloudWatch Logs metric filter, and raises a
  `liquidator-catch-cycle-stale` alarm when there is no catch cycle for two consecutive
  5-minute periods. This is P0 liveness detection for the ECS task, RPC, chain progress, and
  bot loop. The alarm's `ALARM` / `OK` / `INSUFFICIENT_DATA` actions publish to the backend
  alarm SNS topic. If `JPYDF_BACKEND_ALARM_TOPIC_ARN` is present, use the existing incident
  topic in the same region; if absent, `BackendStack` creates the topic and outputs it as
  `BackendAlarmTopicArn`.
- `BackendStack` also aggregates the initial failure alarms of the scheduled workers into
  the same backend alarm SNS topic. The stats publisher always has the EventBridge
  `FailedInvocations` and `publish-stats-s3 failed:` log metric filter / alarm. In addition,
  when the public stats `healthStatus` becomes `critical` / `warning`, the stats publisher
  emits structured JSON logs with `source="publish-stats-s3"`, `ok=false`, and
  `severity="critical" | "warning"` to CloudWatch Logs. JSON metric filters alarm to the
  same SNS topic. This delivers the Ops Dashboard's buffer shortfall / buffer target warning
  and the like to email / ChatOps even without constant on-screen monitoring. When
  `route-interest` is enabled, it also creates the EventBridge
  `FailedInvocations` and `route-interest failed:` log metric filter / alarm. These publish
  the `ALARM` / `OK` actions to the backend alarm SNS topic, and treat missing data as
  non-breaching.
  When a comma-separated email list is set in `JPYDF_BACKEND_ALARM_EMAILS`, `BackendStack`
  also creates an SNS email subscription. The email subscription requires
  `JPYDF_BACKEND_ENABLED=true`. SNS email is not delivered until the recipient approves the
  AWS confirmation email. `pnpm -C infra/cdk check:backend-alerts` checks the CloudFormation
  output, the SNS confirmed subscription, the CloudWatch alarm action, the SNS topic policy's
  HTTPS-only publish deny, its CloudWatch publish allow restricted to the same account and the
  current Backend stack alarm-name prefix, the scheduled worker alarm state, and the ECS steady
  state when the liquidator is enabled, all together, and fails if recipient confirmation is
  incomplete.
  After at least one receiver is confirmed,
  `JPYDF_BACKEND_ALERT_TEST_CONFIRM=send pnpm -C infra/cdk publish:backend-alert-test`
  publishes a one-off test message to the backend alarm SNS topic, leaving evidence that
  notifications are actually received. This delivery test is not sent unless the explicit
  confirm env and a confirmed subscription are present. This direct SNS test proves only
  topic-to-receiver delivery; it does not exercise the log metric filter or CloudWatch
  alarm. Before declaring production readiness, use a clearly labeled stats-health JSON
  test incident in staging and verify the metric-filter match, alarm `ALARM` / `OK`
  transitions, and receipt by the same receiver. Record the log stream, alarm history,
  receiver, receipt time, and resolution time as non-secret evidence.
  ChatOps / PagerDuty subscriptions, escalation policy, and dashboards are pinned separately
  on the ObservabilityStack or external incident tooling side.
- Enable live submission only when the Secrets Manager signing key, KMS, task role, positive
  gas/loss caps, chainId check, and receipt timeout alert are satisfied.
- Automatic SP top-up / atomic JIT bundle / collateral disposal are out of the current bot
  scope, so do not mix them into the hosting plan either.
- Treat `route-interest` as a worker separate from the liquidator, with a separate secret.
  The live mode mounts `IRTR_ROUTE_PRIVATE_KEY` from Secrets Manager only into the live task
  definition, and is enabled only when chainId, the `interestRouter` match across all
  branches, the Forwarder `jpydfToken()`, the expected recipient, a positive minimum route
  amount, and pre-send simulation are satisfied. The dry-run task definition does not attach
  the signer secret.

### Mainnet fork stress rehearsal

- `mainnet-fork-evidence` runs in a CodeBuild project. GitHub Actions only invokes the
  dispatcher Lambda via an AWS role through OIDC. Do not make operator local output alone the
  production evidence.
- The CDK backend stack creates `ForkStressGateProjectName`,
  `ForkStressDispatcherFunctionName`, `ForkStressGithubDispatchRoleArn`, and
  `ForkStressEvidenceBucketName` only when `JPYDF_FORK_STRESS_ENABLED=true`. They are not
  created in the default synth / deploy.
- GitHub Actions does not pass a CodeBuild `source-version`. The dispatcher Lambda validates
  only `FORK_BLOCK` / scenario id / optional launch config, and starts the CodeBuild project
  at a fixed source ref with no source / buildspec / image / artifact / secret env override.
  Do not let manual input run an arbitrary ref / branch / commit on CodeBuild with secrets.
- The standard buildspec for CodeBuild is
  `infra/cdk/buildspecs/mainnet-fork-stress-gate.yml`, and the manual GitHub Actions entry
  point is `.github/workflows/mainnet-fork-stress-gate.yml`.
- `MAINNET_RPC_URL` is an archive-capable RPC, placed in Secrets Manager / SSM Parameter
  Store. Do not place it in GitHub repository / environment secrets.
- The frozen deploy / handover env is passed to CodeBuild as the Secrets Manager
  `DF_DEPLOY_ENV_FILE`. The buildspec does not source this as a shell; it exports only
  literal `KEY=value` pairs for `DF_*` / `DEPLOYER` / `DEPLOYMENT_MODE` / `SALT` /
  `GAS_ESTIMATE_MULTIPLIER`, and rejects key names that could hold a private key, a raw RPC
  URL, or an unpublished Safe nonce.
- `DEPLOYER` is a public address for anvil impersonation; do not pass a private key.
- The GitHub OIDC dispatch role is limited to the dispatcher `lambda:InvokeFunction` /
  `codebuild:BatchGetBuilds`, and the trust policy is narrowed to the branch / tag patterns
  permitted for production evidence. `codebuild:StartBuild` is held only by the dispatcher
  Lambda execution role.
- Evidence artifacts are stored in a KMS encrypted S3 bucket. For public PRs / docs, paste
  only the scenario id, fork block, status, payload hash, AWS build id, artifact label, and
  secret hygiene summary.
- `JPYDF_FORK_STRESS_BUILD_IMAGE` is an image that includes `forge` / `anvil` / `cast` /
  Node / pnpm. Production requires a digest image and rejects a mutable tag.
- Safe / role holder txs executed in the launch window are matched against the decoded
  calldata of the admin console / Safe artifact and the fork rehearsal input hash.
- When the historical stress block is before the existence of a Day-1 external dependency, do
  not treat it as a PASS of the full deploy rehearsal. Supplement with observation of the
  target asset / external protocol, synthetic stress of the current fork, and unit /
  invariant / targeted fork tests.

### Subgraph

- On Day-1, use a managed / hosted subgraph endpoint, and the AWS CDK handles only the
  endpoint URL and the freshness monitor.
- If self-hosting becomes necessary, design it as a separate stack with Graph Node, RDS
  Postgres, IPFS / EFS, indexer snapshot backup, schema migration, and a replay plan.

## 4. Provider Portability

The CDK implementation creates the actual entities on AWS, but the following boundaries are
maintained across providers.

| Boundary | AWS Day-1 | Portable alternative | Rule |
| --- | --- | --- | --- |
| User app hosting | S3 private bucket + CloudFront OAC | Vercel, another CloudFront distribution, static hosting with private origin | Make `frontend/app/out` an immutable artifact, and pin hosting-specific env in the build evidence. |
| Ops dashboard hosting | S3 + CloudFront | Vercel / Render static / separate CDN | Maintain the rule of separating the hostname / project / key from the user app even after a provider change. |
| Admin console hosting | ALB auth + ECS nginx | Cloudflare Access / Vercel Enterprise auth / Render private service | Prioritize the auth wall, MFA, noindex, non-linking from the user app, and non-holding of secrets over the hosting provider. |
| Public stats storage | S3 + CloudFront | R2 / Vercel Blob / managed object storage | Pin the JSON schema, freshness fields, and stale behavior, and swap only the URL. |
| Staging dev RPC | ECS Fargate Anvil + ALB + CloudFront | Render private service / Fly / local tunnel for short drills | Clearly separate the display from production, and pin the chainId / manifest / reset evidence per release. |
| Worker runtime | ECS Fargate scheduled task/service | Render worker / Fly / Kubernetes / GitHub Actions for low-frequency jobs | Keep the entrypoint and env contract stable, and separately produce evidence of restart / state semantics for a stateful keeper. |
| Worker state | EFS, later DynamoDB/S3 | Neon / Postgres / Redis / managed durable storage | Pin the liquidator cursor / idempotency key / replay behavior as a schema. |
| Fork stress rehearsal | GitHub OIDC dispatch + CodeBuild + archive RPC + Foundry / Anvil + S3 evidence | Self-hosted runner / ECS task / another CI with archive RPC | Keep the output schema and payload hash matching stable, and do not emit the RPC secret in the evidence. |
| Relational DB | RDS only if needed | Neon Postgres | Do not add a DB on Day-1. If it becomes necessary, first define schema migration, backup, restore drill, and RLS / network policy. |
| Observability | CloudWatch, Synthetics, SNS | Better Stack, Datadog, Grafana Cloud | Keep the alert names, SLO, runbook links, and redaction policy tool-neutral. |
| DNS / TLS | Route 53 + ACM | Cloudflare / external registrar | Record the official URL table, registrar lock, owner, and break-glass independently of the provider. |

Migration-ready requirements:

- Store the build output as an immutable artifact that does not depend on a provider-specific API.
- Express the runtime config with generated env / manifest hash / URL table, and do not
  hardcode a protocol address inside a CDK construct.
- Manage the public stats JSON's consumer contract by schema version, and do not change the
  user app's stale / unavailable behavior even when the storage provider changes.
- Document the worker's contract of `command + env + secret refs + state backend`, and do
  not place business logic on ECS-specific events.
- Do not confine observability to CloudWatch metrics names only; have names and expected
  results that can reproduce the same synthetic checks on an external monitor such as Better
  Stack.

## 6. Environment And Secret Model

KMS is made a standard premise of production hosting. Rather than relying on AWS managed
encryption alone, separate the customer managed KMS key per production / staging, and make
the key policy, rotation, alias, scheduled deletion guardrail, and principal explicit in
CDK.

| Resource | KMS policy |
| --- | --- |
| user app / ops / stats S3 buckets | Enable SSE-KMS. For a bucket read from CloudFront OAC, grant the CloudFront service principal decrypt / data key permissions bound to the distribution ARN via `AWS:SourceArn`. |
| release evidence / log buckets | SSE-KMS. The release evidence bucket is created by CDK and allows only explicit `aws:kms` + stack CMK upload. The release evidence upload role is limited to the repo/ref subject, the release evidence prefix, and the release evidence CMK. Grant decrypt permission only to the CI deploy role, break-glass admin, and audit reader. |
| Secrets Manager | Encrypt the admin OIDC secret, RPC key, and liquidator live signing key with a customer managed KMS key. Do not attach the signing key secret to the dry-run task definition. |
| Mainnet fork stress RPC secret | Only the fork stress job role can read the archive-capable `MAINNET_RPC_URL`. Do not emit the raw URL to the CodeBuild log and artifact. |
| EFS liquidator state | Enable EFS encryption at rest, and grant access point / mount permission only to the liquidator task role and break-glass admin. |
| CloudWatch Logs | Enable KMS encryption for production log groups, and make the retention and export permissions explicit. |
| ECR images | Enable KMS encryption for production worker / console images. |

Lean the KMS key policy toward least privilege. In particular, for CloudFront + S3 +
SSE-KMS, the OAC bucket policy alone is not enough, so also put a CloudFront distribution
ARN condition on the KMS key policy side.

| Data | Storage | Exposure rule |
| --- | --- | --- |
| public contract addresses / chainId / manifest hash | generated env artifact + static bundle | Public, pinned per release. |
| user app RPC URL | build env / public bundle | Treat as public read endpoint. Use domain allowlist, rate cap, rotation owner. |
| browser RPC URL (user app / Ops / Admin) | shared generated `DEPLOYMENT.rpcUrl` or surface-specific runtime config | Treat it as a public read credential visible from browser bundles / authenticated browsers. Sharing is allowed; cover every consuming domain, aggregate traffic rate / capacity, and a rotation owner. The public UI displays only the provider label, and redacts it in evidence. |
| worker RPC URL | Secrets Manager or task env rendered only into ECS / worker runtime | For server-side workers such as `export-stats`, `route-interest`, and liquidator. Do not put it in the browser bundle. |
| WalletConnect project id | build env / public bundle | Public-ish client id; restrict domains where provider supports it. |
| liquidator private key | Secrets Manager + KMS | Only mounted in live task definition. Not present in dry-run task. |
| InterestRouter route private key | Secrets Manager + KMS | Separate from liquidator key. Only mounted in live `route-interest` task definition after route runbook gates pass. |
| archive mainnet RPC URL | Secrets Manager or SSM + KMS | Fork stress rehearsal job only. Not available to frontend bundles or public stats workers. |
| OIDC / Cognito client secret | Secrets Manager | Admin stack only. |
| deployment manifest | versioned artifact in CI and S3 evidence bucket | Hash must match frontend build evidence. |

| Env | Purpose |
| --- | --- |
| `OPS_STATS_S3_BUCKET` / `OPS_STATS_S3_KEY` / `OPS_STATS_S3_REGION` | Stable public stats object destination. |
| `OPS_STATS_S3_VERSIONED_PREFIX` | Immutable versioned stats prefix. |
| `OPS_STATS_S3_CACHE_CONTROL` | Stable object cache policy. Must be <= `OPS_STATS_STALE_THRESHOLD_SEC`. |
| `OPS_STATS_STALE_THRESHOLD_SEC` | Upper bound for stable stats cache age. |
| `OPS_STATS_S3_SSE=aws:kms` / `OPS_STATS_S3_KMS_KEY_ID` | Explicit SSE-KMS publish headers. Required in production mode. |
| `OPS_STATS_REQUIRE_KMS` | Force or disable script-level KMS guard. Production defaults to required. |
| `VITE_OPS_RPC_PROVIDER_LABEL` | Public ops UI RPC label; prevents host / key disclosure. |
| `JPYDF_BACKEND_ALARM_TOPIC_ARN` | Optional same-region existing SNS topic ARN for backend alarm actions. If omitted, `BackendStack` creates a backend alarm topic and outputs its ARN. |
| `JPYDF_BACKEND_ALARM_EMAILS` | Optional comma-separated email receivers for backend alarm SNS subscriptions. Requires `JPYDF_BACKEND_ENABLED=true`. Each receiver must confirm the AWS SNS email before notifications are delivered. |

Production builds must fail closed when required chainId, RPC, subgraph, stats URL,
or deployment manifest values are missing. Missing production values must not
fall back to local defaults, upstream Liquity endpoints, or fixture snapshots.
Local development snapshots such as `frontend/app/public/jpydf-stats-local.json`
must be deleted or excluded before publishing `frontend/app/out` to AWS.

## 7. CI/CD Flow

1. Freeze deployment manifest and generated app env from current contract deploy.
2. Regenerate `frontend/df-shared` and frontend env artifacts.
3. Pin the GraphQL schema source for `frontend/app` build. Use a managed /
   hosted subgraph endpoint with recorded freshness, or a committed schema
   artifact. Production CI must not silently depend on a local Graph Node.
4. Run focused checks:
   - `pnpm --filter @jpydf/app check:data-sources`
   - `pnpm --filter @jpydf/app build`
   - `pnpm --filter @jpydf/ops build`
   - `pnpm --filter @jpydf/console build`
   - `cargo test --manifest-path bots/liquidator/Cargo.toml`
5. Build Docker images for `frontend/console` static nginx, `ops-worker`, and
   `liquidator`. On Day-1, the ops worker builds `frontend/ops/Dockerfile.worker` at the
   root context for `linux/amd64`, and specifies an ECR image that ECS can pull in
   `JPYDF_OPS_WORKER_IMAGE`. The Dockerfile includes `frontend/ops` and
   `frontend/df-shared`. Staging tolerates a mutable tag such as `:staging`, but
   production's `JPYDF_OPS_WORKER_IMAGE` / `JPYDF_LIQUIDATOR_IMAGE` are pinned to an
   immutable image reference of the form `repo@sha256:<digest>`. Since merely repushing the
   same mutable tag in staging does not change CloudFormation's image string, the ECS
   service is not automatically replaced. Replace the task with
   `aws ecs update-service --force-new-deployment`, and leave the new task's `imageDigest`
   and CloudWatch startup log as evidence. Do not treat the GHCR placeholder as the default.
6. Publish artifacts with immutable build identifiers.
   - For user app static uploads, exclude local-only stats snapshots such as
     `jpydf-stats-local.json`.
   - For public stats uploads, require `OPS_STATS_S3_KMS_KEY_ID` to point to the
     stats bucket CMK, not the AWS-managed `aws/s3` key.
   - Store release evidence in `ReleaseEvidenceBucketName` with
     `--sse aws:kms --sse-kms-key-id <ReleaseEvidenceKmsKeyArn>` through
     `.github/workflows/release-evidence-upload.yml` and the
     `ReleaseEvidenceGithubUploadRoleArn` role.
   - Run `pnpm -C infra/cdk check:release-evidence <file>` before uploading
     release evidence; the workflow runs the same check before `aws s3 cp`.
   - Publish user app / ops static assets through
     `.github/workflows/static-assets-production-publish.yml`, which uses the
     static asset publish role, stack output bucket / KMS / distribution ids,
     SSE-KMS S3 sync, CloudFront invalidation evidence, and a checked
     `release-evidence.generated.json` draft plus replayable
     `static-asset-manifest.generated.json` generated from the published static
     artifact directories.
7. Run [AWS-CDK-IAM-Evidence-Gate.md](../../contributors/deltaforesight/delivery-plans/AWS-CDK-IAM-Evidence-Gate.md)
   checks for synth / diff / assertions / CDK bootstrap readiness /
   GitHub production readiness / production promotion readiness /
   `check:policy-lint` / `check:promotion-evidence` /
   `generate:promotion-release-evidence` / `check:promotion-artifact` /
   `check:production-postdeploy`.
8. Deploy CDK staging.
9. Run negative drills:
   - missing / wrong chainId config
   - RPC all-down
   - stale stats
   - that the stats CDN cache TTL / `Cache-Control` is below the stale threshold
   - stale subgraph
   - public ops raw endpoint / raw error redaction
   - admin unauthenticated access
   - admin CloudFront cache / auth-bypass attempt, if CloudFront fronts ALB
   - hosted Anvil CloudFront `eth_chainId` success and direct ALB `403`
   - stats exporter failure
   - liquidator dry-run restart with persisted state
10. Run `pnpm -C infra/cdk check:cdk-bootstrap` and
    `pnpm -C infra/cdk check:github-production`, then promote to production
    through `.github/workflows/cdk-production-promotion.yml`
    using the GitHub Actions OIDC deploy role and `production-infra` Environment
    subject / branch policy plus explicit deploy confirmation. Deploy runs must
    check AWS live postdeploy state, and the workflow
    must check the promotion diff / outputs / stack-list artifacts, write
    CloudFront invalidation evidence, generate a checked
    `release-evidence.generated.json` draft, replay-check the artifact set, and
    upload those artifacts.
11. Invalidate CloudFront caches when static assets change and record the
    invalidation artifact plus generated static artifact hashes in release
    evidence; replay-check the static publish artifact set with
    `pnpm -C infra/cdk check:static-assets-artifact`.
12. Confirm monitors, alert owners, rollback target, and Go / No-Go.

## 8. Monitoring And Alerts

Minimum monitors:

- user app home / borrow / earn / redeem route renders without raw provider error.
- ops dashboard renders and displays source block / generatedAt.
- public stats JSON freshness stays within threshold.
- subgraph endpoint freshness and GraphQL availability.
- RPC read health per configured browser endpoint / allowed domain; monitor aggregate quota /
  saturation when a key is shared.
- admin console returns unauthenticated denial before login and successful render
  after IdP auth.
- liquidator dry-run service advances blocks and writes state without live tx key.
  CDK P0 counts `starting liquidation catch cycle` with a CloudWatch Logs metric filter,
  and fires a stale alarm when it does not appear for 10 minutes. The alarm actions
  publish to the backend alarm SNS topic. On ALARM, check the ECS service desired/running
  count, the latest task reason, the CloudWatch log stream, RPC/chain progress, and the
  EFS state load log in order. The email receivers managed by
  `JPYDF_BACKEND_ALARM_EMAILS` are notified after SNS confirmation is complete. At T-0
  readiness, leave evidence that `pnpm -C infra/cdk check:backend-alerts` PASSes and that
  the operator received the test message of
  `pnpm -C infra/cdk publish:backend-alert-test`.
- `route-interest` / `publish-stats-s3` scheduled tasks have EventBridge
  `FailedInvocations` alarms and script-failure log metric alarms. On ALARM, check the
  EventBridge target permission, the ECS task stop reason, the worker CloudWatch log, and
  RPC / Secrets Manager availability in order.
- CloudFront 4xx / 5xx, ALB auth failures, WAF blocks, ECS task restarts.
- Even when using an external synthetic monitor such as Better Stack together, use the same
  route / expected status / stale threshold / redaction rule.

Alerts must route to a named operator and link to the relevant runbook. User-facing
failure copy must not expose raw RPC URLs, key fragments, stack traces, or
`DataAPIError` internals.

## 9. No-Go Conditions

Do not launch production hosting if any of these remain:

- the user app / Ops / Admin console share the same public bundle or hostname, or a shared
  browser RPC credential lacks an all-domain allowlist, aggregate rate / capacity limits,
  rotation, or revocation.
- admin console is reachable without company-controlled auth and MFA.
- admin console is fronted by CloudFront with cacheable authenticated responses,
  missing auth cookie / authorization forwarding, or no auth-bypass cache drill.
- admin console can hold a private key or send privileged transactions directly.
- S3 buckets serving public app / ops are public instead of private behind OAC.
- production frontend starts with missing env and fills values from mock / fixture /
  upstream Liquity endpoints.
- `frontend/app` production build depends on an unpinned local Graph Node or
  mutable schema source without recorded subgraph/schema evidence.
- stale stats / stale subgraph is rendered as current live data.
- public stats CDN cache TTL can exceed the documented stale threshold or serve
  stats without `generatedAt`, source block, and schema version.
- public ops UI renders a full RPC URL, key fragment, raw provider error, or
  stack trace.
- RPC all-down still allows borrow / deposit / redeem / claim write flows to start.
- public evidence contains full private RPC URL, key fragment, signer key, Safe
  nonce, or incident-only operator detail.
- rollback target and cache purge procedure are not recorded.
- liquidator live mode is enabled before dry-run evidence, chainId guard,
  gas/loss caps, and key handling are reviewed.
- `route-interest` live mode shares the liquidator signer secret or is enabled
  before route runbook simulation, recipient, threshold, and chainId gates are
  evidenced.

## 10. Implementation Order

1. Add `infra/cdk` scaffold, environment config, and reusable `StaticSiteConstruct`.
2. Deploy staging user app / ops / public stats with private S3 + CloudFront OAC.
3. Add optional hosted Anvil staging RPC and deploy / reset evidence.
4. Run `pnpm -C infra/cdk check:cdk-bootstrap` and
   `pnpm -C infra/cdk check:github-production`, then run GitHub Actions
   production promotion workflow against the real production account and record
   explicit confirmation / diff / outputs / stack list / generated release evidence draft using
   `infra/cdk/templates/production-promotion-first-run-evidence.md`.
5. Add `publish-stats-s3` scheduled ECS Fargate task and stats freshness canary.
6. Add authenticated admin console hosting behind ALB + Cognito/OIDC.
7. Add liquidator dry-run Fargate service with EFS state and catch-cycle stale
   alarm.
8. Run release evidence upload workflow for the first production promotion and
   record object version / KMS evidence in the same first-run evidence package.
9. Gate live liquidator / route-interest workers after operational drills.
10. Decide whether subgraph self-hosting is necessary; if yes, design it as a
   separate Day-2 stack.

## 11. Open Decisions

| Decision | Default | Owner / evidence |
| --- | --- | --- |
| Production AWS account / org layout | Separate company-owned production and staging accounts. | Asset owner list and billing owner. |
| Domain names | user app, ops, admin, stats JSON are distinct. | Official URL table in frontend production evidence. |
| Admin IdP | Cognito or company OIDC; MFA required. | Admin console production evidence. |
| RPC provider key policy | Day-1 allows one browser read-only credential shared by the user app / Ops / Admin. Use per-surface keys only for quota / fault isolation, not as a security boundary. | Redacted provider label, shared / split, all-domain allowlist, aggregate rate / capacity, rotation / revocation. |
| Hosted Anvil reset cadence | Manual reset / redeploy while staging UX is still moving. | Reset evidence, manifest hash, frontend staging warning check. |
| Public stats cadence | Start with short recurring schedule; tune after RPC/provider limits are known. | stats freshness monitor and cost evidence. |
| Liquidator live mode | Off by default. | dry-run evidence, policy caps, signer custody approval. |
| Subgraph hosting | Managed/hosted endpoint for Day-1. | freshness monitor and incident runbook. |
| Vercel / CloudFront posture | AWS CloudFront is Day-1 baseline; Vercel remains viable for user app if the same env, artifact, headers, and rollback evidence are satisfied. | provider comparison and delivery gate evidence. |
| Neon / RDS posture | No DB for Day-1 frontend hosting unless a worker feature requires it. If DB is introduced, Neon and RDS must share migration / backup / restore drills. | schema migration plan and restore evidence. |
| Render / ECS posture | ECS is Day-1 baseline for workers; Render can host non-custodial workers if restart, secret, state, and alert semantics match. | worker runbook and dry-run evidence. |
| Better Stack / CloudWatch posture | CloudWatch is infrastructure source; Better Stack may be external synthetic / incident UX layer. | monitor parity checklist. |
