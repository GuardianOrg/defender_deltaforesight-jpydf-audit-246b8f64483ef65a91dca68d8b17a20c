## Bottom line

- **L-02: defer is defensible, but the stated rationale is wrong and two operational failures are missing.** Removal is not "final abandonment" because a removed Strategy can be re-registered, and the real trap is an *unreadable* residual, not a nonzero one. Recommend: conditional deferral with a documented sunset-upgrade path, plus a small GOV-only deregistration function as the preferred post-launch fix.
- **I-07: the proposed operational control does not address the mechanism.** The over-burn is at most one share per withdraw call regardless of the requested amount, and one caller path chooses its own amount. Recommend: no code change for Day-1 Morpho V2 *if* the lead verifies the venue's virtual-share offset and first-deposit state, and a precise rounding-bound guard or floor-share redeem in the Strategy before any generic ERC-4626 venue is activated.

## L-02: written-off Strategies stay registered

**What the code actually does.** `removeStrategy` at `CollateralVault.sol:658-676` requires principal readable-and-zero and estimate readable-and-zero. Writeoff at `CollateralVault.sol:689-706` only reduces principal through `BaseStrategy.sol:395-405`. A residual position therefore blocks removal in two distinct states, and they behave very differently:

- **Readable nonzero estimate** (Guardian's Morpho V1.1 example). Conservative value is `min(estimate, principal)` at `CollateralVault.sol:1063`, so with principal zero the Strategy contributes zero to every backing view. Cost is one extra pair of external staticcalls per valuation sweep on every price read, plus a slot. This state is operationally harmless.
- **Unreadable estimate** (venue view reverts after upgrade, pause, or bricking). This state is not harmless, and the tentative policy does not mention it. `_managedUnderlying` returns zero when any registered Strategy is unavailable at `CollateralVault.sol:1003-1011`. That makes `allocate` a silent no-op at line 374-375 and makes `transferYieldToTreasury` return zero at line 480-485 for the whole branch. Separately, `_totalUnderlyingWithAvailability` at line 835-844 flags the branch unavailable, so whenever known assets are below liabilities, which is exactly the post-writeoff state, `backingRatioForPricing` returns unavailable at line 861 instead of the haircut ratio. The branch gets an oracle pause rather than repriced Troves. The test at `CollateralVaultStrategy.t.sol:1710-1718` confirms removal is impossible in this state. There is also no gas cap on the `try` at line 1176-1186, so a venue that burns gas on view makes every price read on the branch near-unusable and the Strategy still cannot be removed.

**Challenges to the tentative rationale.**

1. **"Retain to preserve recovery" overstates what removal loses.** The shares live in the Strategy contract, not the Vault. After removal, `receiveFromStrategy` rejects the Strategy at line 404-406, but `addStrategy` at line 601-620 accepts a previously removed address as long as it is still whitelisted and `removeStrategy` never clears the whitelist. Re-registration with weight zero restores the push path, and owner emergency functions then work again. Deregistration is reversible by GOV. The client response should say that rather than implying removal forfeits recovery.
2. **An escape path already exists and should be named.** The Strategy is UUPS-upgradeable by the Timelock at `BaseStrategy.sol:191-193`, and `GOVERNANCE_ROLE_ASSIGNMENT.md:21` confirms the Timelock holds the upgrader role. A sunset implementation whose `_estimatedTotalUnderlying` returns zero and which keeps the emergency redeem function makes `removeStrategy` pass. This is clunky, but it means deferral is not a permanent lock-in, and it uses the same governance tier a new abandonment function would need. That code does not exist today and would be new audit scope when written.
3. **A new abandonment function carries less risk than the policy assumes.** Because the residual already contributes zero to backing, deregistering it changes no solvency number. The only security-relevant effects are freeing the slot, shortening the sweep, restoring availability, and blocking `receiveFromStrategy` until re-add. The governance risk is a lower-threshold role stranding *recoverable* yield, which the existing test at `CollateralVaultStrategy.t.sol:1691-1708` deliberately protects against. That argues for GOV via Timelock, not GUARDIAN, as the caller.
4. **Re-enable hygiene is a real governance risk regardless of disposition.** `updateStrategy` at line 622-641 lets GOV set a written-off Strategy back to enabled with nonzero weight, and re-added Strategies start `enabled: true` at line 615. Operators need an explicit rule against this.

**Minimal fix if you choose to act.** One new function, roughly 15 lines, `onlyRole(GOV_ROLE)`, requiring: registered, `!config.enabled`, principal readable and zero, and either estimate unreadable or estimate nonzero with a caller-supplied acknowledgement amount that must equal the current estimate. It then does the same array swap, config delete, and cache invalidation as `removeStrategy`, and emits the residual estimate. Do not relax `removeStrategy` itself, because that would let the 2-of-5 Guardian strand recoverable yield. Check the Vault's EIP-170 headroom before committing; the remediation doc only records headroom for TroveManager and BorrowerOperations.

**Conditions under which deferral is defensible.** All of these must hold:

- Day-1 registrations are few. The docs show Aave plus one Morpho V2 slot on branch 1, so 32 slots are not a launch constraint.
- The runbook treats "writeoff done, estimate unreadable" as a branch-level incident, not a cleanup item, because allocation and yield sweeps on that branch are dead and pricing can go unavailable.
- The sunset-upgrade path is written down as the recovery procedure, with the storage-layout constraint noted.
- Monitoring alerts on `StrategyValuationRefreshFailed` and `StrategyAllocationSkipped` and on any read where a registered Strategy's valuation is unavailable.
- Governance policy forbids `updateStrategy` re-enabling a written-off Strategy and documents re-registration with weight zero as the post-removal recovery step.

**Suggested client response.** "We acknowledge that a written-off Strategy with a nonzero or unreadable upstream valuation cannot be removed and continues to occupy a slot and appear in valuation sweeps. A nonzero readable residual contributes zero to backing after writeoff. An unreadable residual is more serious: it disables allocation and treasury sweeps on the branch and can make pricing unavailable, and we treat that state as an incident with a Strategy implementation upgrade as the current resolution path. We are deferring a dedicated deregistration function pending governance design for who may deregister a residual position, and we note that a removed Strategy remains re-registrable so deregistration is not irreversible. This is not a code fix or formal risk acceptance."

## I-07: ERC-4626 ceil-withdraw rounding

**Mechanism, precisely.** `ERC4626Strategy._doWithdraw` at `ERC4626Strategy.sol:93-118` sizes the request with floor `convertToAssets` at line 97, then calls `withdraw(assets)` at line 105, which burns `ceil` shares. The checks at lines 113-114 pass because the Strategy did receive exactly the requested assets. `MorphoV2Strategy.withdrawFromMorphoVault` at `MorphoV2Strategy.sol:236-254` has the same shape. The over-burn is bounded at one share per call. Loss materiality is therefore a single number: the asset value of one share relative to the position. It is *not* a function of the requested amount.

**Reachable example with the repo's own mock.** With `MockERC4626Vault` (OpenZeppelin math, offset zero): seed one share, donate so total assets are 100, then have the Vault allocate 101. The Strategy gets exactly two shares valued at 101, so the post-allocate backing check passes. Any `sendToVault` for 1 through 50 units burns one share and loses about 50 units. A request for 51 burns two shares and loses about 50 as well. The existing tests at `ERC4626Strategy.t.sol:464-533` cover only the deposit-side case. No local test covers the withdraw side; Guardian's PoC is external.

**Challenges to the tentative policy.**

1. **"Reject dust recalls" is the wrong control.** As shown above, a non-dust recall loses the same amount. If one share represents material principal, no `sendToVault` amount is safe except exact whole-share multiples. The correct admission and monitoring criterion is "value of one share is dust", which is a venue property driven by its virtual-share or decimals offset and its current supply.
2. **One caller path chooses its own amount.** `sendProfitToVault` at `BaseStrategy.sol:360-392` computes `realizedYield` internally and calls `_doWithdraw` with it. A donation inflates the Strategy's estimate, which makes `realizedYield` nonzero, which is precisely when a periodic harvest runs. Operator policy cannot size that request. The loss is still bounded at one share, but the "operators must not call with dust" language cannot be enforced on this path.
3. **The allocate-side backing check is not a rounding guard.** `_requireConfirmedFullyBacked` at `CollateralVault.sol:899-916` compares raw balance including backstop reserve and unswept yield against liabilities. Rounding loss at deposit up to the current surplus is silently accepted; the test at `ERC4626Strategy.t.sol:503-533` demonstrates the backstop absorbing it. An attacker who front-runs `allocate` can also align the donation to the observed buffer excess so no deposit-side loss appears at all.
4. **Morpho V2 retry loop compounds a naive guard.** If a rounding guard is added inside the isolated frame, the halving loop at `MorphoV2Strategy.sol:219-226` will retry seven times uselessly because halving does not change the one-share bound. Any guard belongs before the loop.

**Generic exchange-rate guard: do not add.** A guard of the form "revert if `convertToAssets(ownShares) < principal`" would block `sendToVault` during a genuine venue loss, which is exactly when recovery matters. That is the wrong tool and the policy is right to avoid it.

**Precise rounding-loss bound: cheap and does not block loss recovery.** Two options, both venue-agnostic and both leaving exchange-rate losses recoverable:

- **Option A, floor-share redeem.** Compute `shares = convertToShares(assets)`, return zero if it floors to zero, call `redeem(shares)`, and check delivered assets against `previewRedeem(shares)`. The Strategy never burns more value than it receives. It changes the `actual == requested` invariant to `actual <= requested`, which `sendToVault` and `sendProfitToVault` already tolerate. About 10 lines per Strategy, plus updating the mismatch tests. Structurally the correct fix.
- **Option B, two-line guard.** Before the venue call, require `previewRedeem(previewWithdraw(assets)) <= assets + tolerance`, with a small fixed tolerance in underlying base units. It rejects only the state where one share is worth more than dust and has no dependence on principal or exchange rate. Fail-closed on `sendToVault`; the owner-only `emergencyWithdrawFromERC4626` redeem path at `ERC4626Strategy.sol:147-176` still drains. For Morpho V2, place it before the retry loop.

**Recommendation.**

- **Day-1 Morpho V2:** conditional deferral. The lead must verify from the venue code and state, not from documentation, that the vault applies a virtual-share offset and that per-share value at admission is dust relative to the planned cap. If either fails, apply Option B to `MorphoV2Strategy` before activation. Do not make the case rest on "operators will avoid dust".
- **Generic `ERC4626Strategy`:** it is not Day-1 active per `Contract-Business-Catalog.md:30`, so there is no launch cost to fixing it, only re-review identity. Apply Option A or B before any generic ERC-4626 venue is activated, and add a withdraw-side test mirroring the example above.
- **Operational controls that are actually enforceable:** admission readback of `convertToAssets(1 share)` and the offset, a monitor on that value with an alert threshold tied to the branch cap, and a rule that share-price anomalies pause harvests.

**Suggested client response.** "We acknowledge that the standard ERC-4626 ceiling withdraw can burn up to one whole share more than the requested assets, and that in a donation-inflated venue one share can represent material principal. The exposure per call is bounded by the value of one share and does not depend on the requested amount, so our control is venue-level: approved venues must show virtual-share or offset protection and a per-share value that is negligible relative to the Strategy cap, monitored continuously. We are not adding a generic exchange-rate guard because it would block recovery during real venue losses. A precise rounding-bound check in the Strategy remains under consideration for venues that cannot demonstrate the above. This reduces but does not eliminate the exposure."

**What was not verified.** Live Morpho V2 vault offset, supply, and first-deposit state; the Vault contract's EIP-170 headroom; Guardian's external PoC. Those are for the lead.
